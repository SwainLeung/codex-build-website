# 把一项变更交给评审

输入包括仓库、Issue 或目标、用户可观察的结果。先读根目录 `AGENTS.md`、`docs/harness/PROJECT.md`、当前目录说明和关联规格。若需求仍处于收集阶段，按 `docs/harness/IDEAS.md` 记录评估所缺的信息。

1. **找出改动入口。** 列出用户入口、当前行为、调用方与一条可复现的验证路径。对已存在的测试和配置给出仓库内路径。
2. **写清验收。** 给每条要求一个编号。描述前置状态、输入、动作、预期输出或副作用。涉及持久化、并发、重试或旧数据时，为实际风险增加验收场景。复杂变更从 `docs/harness/SPEC.md` 建一份任务规格，小改动直接更新 Issue。
3. **实施并验证。** 复用仓库现有实现。为变化行为增加或调整相应检查，先验证最小受影响面，再在仓库根执行 `python3 scripts/harness.py check`。对故障修复保留原问题的回归证据，将未运行的验证标明原因。
4. **准备交付。** 按 PR 模板填写 Issue、影响范围、每项验收证据、实际执行的命令和风险。列出版本记录或发布单需要更新的内容。流程或规则变更还应更新对应指令或项目卡。

完成标准是评审者能够按证据复测每项验收，并能看到尚待处理的风险。生产部署由发布单承接。
